# 提案から結果公開までの運用フロー

このプロジェクトは市民による公開提案です。GitHubの進捗状態は調査と議論の進み具合を示します。自治体による採択、予算化、実証の許可を意味しません。

## 参加する人の役割

| 役割 | 主な仕事 | 判断できること |
| --- | --- | --- |
| 提案者 | 課題や改善案を送る。分かる範囲で地域と根拠を示す | 提案と追記。匿名フォームからの投稿も可能 |
| コントリビューター | 出典調査、試算、文章・サイトの修正、実証案の設計を行う | IssueとPRで変更を提案する |
| メンテナー | 匿名投稿の審査、Issueの整理、PRの確認、進捗と判断理由の公開を行う | このリポジトリ内の公開・統合・状態変更を決める |
| 実証の実施主体 | 自治体・企業・大学など、必要な権限と責任を持って実施する | 各組織の正式な手続に従い、実証の実施を決める |

メンテナーの判断は、このプロジェクトの掲載と作業順序に限ります。政策や設備投資の決定権を代行しません。

## まず何をするか

1. **課題やアイデアを出す**：GitHubを使う人は[Issue](https://github.com/kechirojp/kibi-innovation-project/issues/new/choose)、使わない人は[匿名フォーム](https://kibi-innovation-project.pages.dev/#proposal)へ。個人情報や第三者を特定できる情報は書かないでください。
2. **既存の課題を進める**：[公開ボード](https://github.com/users/kechirojp/projects/2/views/1)からIssueを選び、「何を調べるか」をコメントします。作業の重複を避けたいときは、着手前に担当を相談してください。
3. **文書やサイトを直す**：[参加ガイド](../CONTRIBUTING.md)を読み、PRを送ります。小さな誤記はIssueなしで修正できます。

## ボードの状態と次へ進む条件

| 状態 | 主な作業 | 次へ進む条件・記録 |
| --- | --- | --- |
| 提案 | 課題、対象地域、既存Issueとの重複、公開に適した内容かを確認 | 調べる問いと担当候補をIssueに記す。対象外なら理由をコメントして閉じる |
| 事実確認 | 一次資料、確認日、既存制度、対象規模、反証や不明点を調べる | 確認済みの事実と仮説を分け、出典と未確認点をIssueに記す |
| 実証準備 | 実施主体、費用、資金源、許認可、安全・環境・個人情報、測定方法を整理 | 実施主体の正式な判断と、公開可能な計画・中止条件がそろう。そろわなければこの状態に留める |
| 実証中 | 正式に始まった実証の進捗、費用、測定値、問題を記録 | 実測結果と計画との差を集め、評価と公開の準備をする |
| 結果公開 | 成功・失敗・中止を含め、費用、効果、限界、次の判断を公開 | 結果へのリンクと判断理由をIssueに残して閉じる。追試や改訂は新しいIssueにする |

提案が直接「実証中」へ飛ぶことは避けます。調査だけで価値がある課題は、実証せずに調査結果を公開して閉じられます。状態変更のたびに、担当者、変更理由、次の作業をIssueへコメントします。

## PRの確認と公開

1. PRには変更したページ、根拠、未確認点、表示や動作の確認結果を書きます。
2. メンテナーは出典、事実と提案の区別、個人情報、読みやすさ、既存の方針との整合を確認します。コード変更は自動検証の結果も見ます。
3. 修正が必要ならPRで具体的に伝えます。採用しない場合も理由を残します。
4. 統合後はサイトの公開版を確認し、関連Issueに変更先を記します。

投稿受付、D1、認証、個人情報の扱いを変えるPRは、変更者以外による確認と本番相当の動作確認が済むまで統合しません。確認できる人がいない場合は保留します。

## 判断の透明性

- Issueを閉じるときは「採用」「保留」「対象外」「重複」「調査結果を公開」のいずれかと理由をコメントします。
- 費用・効果の見込みと実測は分けて記載します。出典を更新したときは確認日を残します。
- 意見が割れた場合は、少数意見と未解決の論点をIssueに残します。人格への評価はしません。
- 調達や助成の提案は、評価基準と利益相反の申告方法を実施前に公開します。メンテナーの掲載判断だけで事業者を選びません。

## 他自治体での利用

フォークして地域条件、調査結果、指標を置き換えられます。元の資料への出典と変更履歴を残し、役立った改良はPRで本流へ戻してください。
